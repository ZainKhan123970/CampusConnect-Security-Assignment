# Assignment #2 — CLO-2: CampusConnect Student Portal

## Part A — Security Measures & Tools

### Q1. Selecting Security Measures

**1. Parameterized SQL queries (prepared statements)**
- **Purpose:** Keep user input separate from SQL commands.
- **Risk addressed:** SQL Injection, where an attacker enters SQL code in a login field to change the meaning of a database query.
- **Application:** Use SQLite placeholders (`?`) and pass username as a separate parameter in the login query. The secure route in `server.js` uses `WHERE username = ?` with `[username.trim()]`.

**2. Multer upload validation and private file storage**
- **Purpose:** Control which files users can upload and prevent uploaded files from being directly accessible as public resources.
- **Risk addressed:** Malicious or unexpected files, oversized uploads, and unauthorized access to uploaded content.
- **Application:** Use Multer to accept JPG/PNG only, enforce a 2 MB limit, check the file signature, generate a random filename, and store the file in `private_uploads/` outside the public web folder. Serve it only through an authenticated route.

### Q2. Applying Security Controls

**a) Login protection:** Use a parameterized SQLite query instead of joining username/password input into an SQL string. Store password hashes using bcrypt, compare the entered password with `bcrypt.compareSync`, and limit repeated login attempts with `express-rate-limit`.

**b) File-upload protection:** Use Multer with a 2 MB maximum size, allow only JPG/PNG MIME types and extensions, verify the actual JPEG/PNG file signature, generate a UUID filename, and store the file outside the public directory. Require a logged-in session to upload or retrieve a picture.

## Part B — Practical Implementation

### Task 1 — Protect the Login System

**Insecure implementation:** `POST /demo/insecure-login` is included only to show the unsafe pattern. It builds an SQL query by inserting input directly into the query string.

**Applied security measure:** The secure `POST /login` route uses a parameterized query:
`SELECT id, username, password_hash FROM students WHERE username = ?`

The username is supplied separately as a parameter. The password is verified against a bcrypt hash. This prevents the entered username from being interpreted as SQL syntax.

**Testing:**
1. Start the app and open `http://localhost:3000`.
2. Log in with username `student` and password `Campus@123`. Expected: `Login successful`.
3. Try a wrong password. Expected: `Invalid username or password`.
4. Try SQL-injection-style input such as username `' OR '1'='1` and any password. Expected: login rejected.
5. Optional: send repeated invalid login attempts; the rate limiter eventually blocks further attempts.

### Task 2 — Protect the File Upload Functionality

**Controls applied:**
- JPG and PNG extension and MIME-type allowlist.
- Actual file-signature check (JPEG/PNG magic bytes).
- Maximum upload size of 2 MB.
- Random UUID filename generated by the server.
- Files saved in `private_uploads/`, not in the public static folder.
- Upload and image retrieval require a logged-in session.

**Testing:**
1. Log in first.
2. Upload a real JPG or PNG smaller than 2 MB. Expected: successful upload message.
3. Upload a PDF, TXT, or other unsupported file. Expected: rejection.
4. Upload an image larger than 2 MB. Expected: rejection.
5. Try uploading while logged out. Expected: HTTP 401, `Please log in first`.

## Viva Preparation

- **What is SQL Injection?** It is an attack in which untrusted input changes the intended SQL query.
- **How does a parameterized query help?** It sends SQL code and user values separately, so input is treated as data rather than SQL syntax.
- **Why hash passwords?** A hash avoids storing readable passwords in the database.
- **Why validate file type twice?** Extension and MIME type can be forged; checking the file signature provides an additional check of the actual content.
- **Why use random filenames?** They prevent users from choosing paths or predictable names that could overwrite other files.
- **Why store uploads outside `public`?** The web server cannot serve them as public static files; access goes through the authenticated route.

## Important Notes
